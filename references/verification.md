# 验收规则（连跑 3 次）

## 通过标准

对**本次生成的全部用例**连续执行 `pytest` N 次（默认 **N = 3**，可用 `--count` 调整），判定：

| 判定 | 含义 | 是否通过 |
|------|------|---------|
| `STABLE` | N 次全部 passed | ✅ |
| `FLAKY` | 有时通过有时失败 | ❌ 必须修复 |
| `BROKEN` | N 次全部失败 | ❌ 必须修复 |
| `SKIPPED` | N 次全部跳过 | ⚠️ 需说明原因（通常不该出现） |
| `MISSING` | 用例根本没被收集到 | ❌ 检查文件名/命名是否被 pytest 识别 |

**只有 `FLAKY = 0` 且 `BROKEN = 0` 才算验收通过。**

## 执行命令

```bash
python <skill>/scripts/verify_stability.py \
    --project <自动化工程根目录> \
    --target  <测试文件相对路径或 nodeid> \
    --count 3 \
    --report-dir <project>/.stability
```

可用 `--pytest-args` 透传参数，例如：
- `-m smoke` 只跑冒烟
- `-p no:randomly` 关闭随机执行（提高可复现性）
- `--count 1` 配合 `-x` 快速定位首次失败

## 输出物

- `.stability/stability_report.md` —— 人读：判定汇总表 + 失败原文
- `.stability/stability_report.json` —— 机读：每条用例的各轮状态、分类、建议

退出码：`0` 全部稳定；`1` 存在 FLAKY/BROKEN。

## flaky 判定要点

- 同一条用例在不同轮次状态不同 → 一定是脚本或环境的问题，**不允许通过重跑掩盖**。
- 常见 flaky 根因按出现频率：数据依赖 > 元素等待不足 > 用例间顺序依赖 > 服务抖动。
- 若**所有**用例在某一轮集体失败，优先怀疑被测服务/数据库不可用，而不是改脚本；
  此时应报告用户确认环境后再继续。

## 自愈循环上限

自动修复最多 **2 轮**（改 → 跑 3 次 → 再改 → 再跑）。第 2 轮仍不通过就停止自动修改，
输出：已尝试的改动清单、每轮判定结果、剩余失败的根因判断、需要用户确认的事项。
